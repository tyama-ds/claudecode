# 速度・精度監査への対応（2026-09-14）

対象は `e5740617fd52fbfd28250a2ce8289aa06f590546` の調査・検証経路です。検索結果を取り違える不具合や検証の誤合格を修正し、同じ資料の取得と生成の重複を減らします。

## 修正内容

|対象|変更後の動作|
|---|---|
|検証の異常応答|チャンクごとの応答スキーマを検証し、限定回数だけ再試行。型不正、事実文からの空抽出、部分失敗を正常な検証結果として保存・再利用しません。|
|重要主張|根拠を確認できない critical 主張は ACCEPT にせず、追加調査または未解決として扱います。|
|高速バッチの出典|応答順ではなく page_id で本文と評価を対応付けます。欠落・重複・未知のIDや不正スコアは失敗とし、関連度0.5などの仮の成功値を入れません。|
|取得・抽出の再利用|正規化URLによる実行内キャッシュで同時取得をまとめます。抽出は本文・問い合わせ・モデル・入力予算などをキーに再利用します。失敗はキャッシュしません。|
|追検索|同じURLでも新しい質問なら原文を再利用して再抽出します。新しい情報を既存資料に統合し、独立した出典数を水増ししません。|
|並列処理|標準経路は章内の資料処理を最大4並列、強化統合の論点作成も最大4並列にします。既存の実行・プロセス上限を共有します。検索は明示的に同時実行対応を表明したクライアントのみ並列化します。|
|高速モードの待機|全ページの取得完了を待たず、先に揃ったバッチから評価します。キューと評価ジョブ数に上限を設け、出力は検索順位を保ちます。|
|強化統合|統合本文と要約を同じ応答で生成し、要約専用の追加呼び出しを削減します。|
|追加の全文推敲|V1は不足・低信頼の章を補強対象とし、原文を再取得せず証拠庫から利用します。V2の追加推敲は整合性診断などで必要と判断した章を対象にします。|
|推敲による改変|数値・単位・引用ID・見出し・URL・既知用語を比較し、保護対象が変わった推敲は採用しません。事実の意味の検証は引き続き最終検証が担当します。|
|長い資料|全文原文を保持し、入力予算内で関連箇所を選択します。長大段落も分割し、文字位置を保存します。検証索引の先頭60チャンク制限を除きます。|
|原典文書|高速経路でもPDF・表計算などのリンクを上限付きで追跡します。既定上限は1ページ2件、1回のクロール全体6件です。親ページの抽出失敗が、取得済み文書の処理を妨げないようにします。|
|多言語検索|別の発行元の同名資料をタイトルだけで除外しません。検索順位・関連度を統合順に反映し、同じ翻訳要求を再利用します。|
|日付|公表日・更新日・対象期間・施行日・取得日を区別し、抽出根拠を保持します。本文中の最初の日付を公表日と推定せず、公表日・更新日の未来値は拒否します。|
|資料構造|DOCXの段落と表を元の順序で読みます。ローカルPDFのページ範囲と未抽出ページを記録します。|
|ドメイン|ホスト境界を確認し、`who.int.example.com` などを公式ドメインとして扱いません。|
|通信・停止|HTTPの待機・再試行に残り時間を適用し、本文を少しずつ受信する場合も締切を確認します。停止後に新しい検索・取得・LLM処理を開始しないよう、処理開始時と同時実行枠の取得後に確認します。|

URLキャッシュは追跡パラメータとフラグメントを除外しますが、年度など意味のあるクエリは保持します。キャッシュは実行ごとに初期化します。原文とURLが同じで抜粋だけが異なる資料は同じ証拠にまとめ、更新された原文は別版として保持します。内容が一致する資料の重複は調査の資料数から除外しますが、転載関係や発行主体の独立性すべてを自動判定できるわけではありません。

## 設定と互換性

通常利用で新しい設定は必要ありません。`parallel_max_workers` が引き続き全体の上限です。Seleniumなど単一ブラウザーを共有する経路は直列アクセスを維持します。

V2の `enable_polish=True` は追加推敲を有効にしますが、今回から対象を必要な章に絞ります。全文推敲を省いた章も最終検証の対象です。検証キャッシュのバージョンを更新しているため、旧判定のキャッシュは再利用しません。

画像PDFのOCRは明示的に `DocumentReader(enable_ocr=True, ocr_language="jpn+eng")` を指定した場合に限って使用します。PyMuPDFとTesseractおよび指定言語のデータが必要です。通常のPDFテキスト抽出は既存の依存関係で動き、読めなかったページはメタデータに残ります。OCRの実行速度と認識精度は今回の実測対象外です。

## 計測

正常終了時に出力先へ `performance_<session_id>.json` を保存し、`run()` の戻り値にも `performance` と `performance_json` を追加します。レポート本文に計測情報を混ぜません。

このファイルには工程別の呼び出し回数・所要秒数・失敗数、トークン利用量、観測した同時実行数、ページ取得と抽出のキャッシュ命中数を含みます。`research_details` では検索・取得・抽出・統合を分けて記録します。失敗数は例外の数であり、通常の戻り値に含まれる取得エラーは従来の警告・エラー情報で確認します。並列処理や入れ子の工程の秒数は重複するので、合計を実行全体の経過時間として使わないでください。高速クロールの `total_wall_time` は取得と評価の重複を除いた経過時間です。

実サービスで比較するときは同じテーマ・モデル・資料・設定を使い、総時間、工程時間、呼び出し数、引用元との一致、数値・期間の正確性を併せて確認します。この修正のテスト時間から実調査全体の高速化率は算出していません。

リポジトリのルートで実行します。

```bash
python -B -m pytest -q -rs -p no:cacheprovider deep_research_tool/tests
```

Windowsで既存テストの文字コードに問題が出る場合は、実行前にPowerShellで `$env:PYTHONUTF8='1'` を設定します。

追加したテストは次の5ファイルです。

- `tests/test_research_speed_accuracy.py`: 重複取得・問い合わせ別の再抽出・並列数と順序・入力予算・停止。

回帰テストは固定応答と模擬クライアントを中心に実行します。通信締切はローカルHTTPサーバーから少量ずつ本文を送るケースでも確認します。有料APIを使った実調査の時間比較や、人手による大規模な回答品質評価は含みません。
